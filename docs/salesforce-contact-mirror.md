# Salesforce Contact mirror: first stage

The Contact mirror is a private, read-only copy of a small set of Salesforce fields. It is **off by default**. Enable it on Connections after reviewing the Salesforce org shown there and confirming that the integration user has read access to all Contacts intended for this workspace. The existing audience snapshots, suppression ledger, campaign eligibility checks, and sending path do not read this table yet.

Mirror exclusions use the same nested AND/OR Contact condition builder as audiences. For example, exclude `Opt_out_ALL_Comms__c = true` OR `Contact_Type__c = Child`. The supported operators depend on the field type, including greater than or equal to for numbers and dates, and contains for text. Only filterable stored Contact fields and the three reviewed Contact-only formulas can be used. `Contact_Type_Age__c` is deliberately unavailable: its `TODAY()` formula can change without a Contact update. Exclusion fields need not be selected for storage. Pause the mirror to change rules; saving starts a full rescan. The scan copies nonmatching Contacts, then removes matching rows already copied, and each later incremental cycle also removes Contacts that have become excluded. Wait for a complete scan before relying on the new rules. These exclusions do not alter Salesforce records or the separate consent ledger.

By default, the mirror stores Contact ID, email, first and last name, `HasOptedOutOfEmail`, and `SystemModstamp`, keyed by Salesforce org and Contact ID. In Connections, the browser searches every Contact field visible to the connected Salesforce user; the **30 max** label limits how many additional fields you can select, not how many you can search. You can select direct scalar Contact fields. Three reviewed Salesforce formulas are also selectable: `Donor_Type__c`, `mito_Registry__c`, and `All_Mito_Connections__c`. Their formulas currently depend only on stored fields on the same Contact, so Salesforce calculates their values when the existing Contact sync queries them. If a formula definition changes, review its dependencies and rebuild the mirror; a formula edit alone does not update Contact `SystemModstamp`. Other calculated fields, long text, encrypted, compound, and always-included fields remain visible with an explanation but cannot be selected. Related-object fields require Salesforce audience queries and do not appear in the Contact field list. Only select fields needed for segmentation or personalization. Pause the mirror before changing the selection. Saving it clears previously copied optional values and resets the mirror to a full scan; re-enable it to populate the new selection. The status API returns selected field names, progress, and errors, never Contact values.

The table and its sync state live in the private `forcemultiplier` schema; anonymous and authenticated Supabase roles have no table grant or RLS policy. The application accesses them only on the server through its database connection. Deleted Contacts clear email, name, and optional values from the local row. Selected fields are stored as server-only JSON per Contact, with a size limit and validation; a malformed page fails without advancing the checkpoint. Related-object fields remain available in audience queries but are not mirrored here.

The first scan pages through every nonexcluded Contact up to a fixed time boundary, then pages through excluded IDs and removes their old mirror rows. Each page and its checkpoint commit together. A completed scan marks old mirrored rows absent from that scan as deleted, so a rebuild reconciles records removed while the worker was offline. Daily runs overlap the prior `SystemModstamp` watermark, repeat both inclusion and exclusion passes, then consume Salesforce's deleted-record feed. The worker refuses to advance after an incomplete page, an unexpected org change, or a deletion-history gap. It never clears an opt-out in Salesforce or the suppression ledger. Source permissions matter: this mirror contains only records visible to the connected Salesforce user; a permission change can make a rebuild mark unseen rows deleted.

The scheduled worker uses `CRON_SECRET` and processes up to 2,000 Contacts per minute while enabled; a million-record initial scan therefore takes at least about eight hours. The Connections card can pause it or run the next step manually and shows the last completed full-scan count. A failed step retains its last committed checkpoint and shows a safe error. After a long outage, the deleted-record feed may no longer cover the gap; use the authenticated `POST /api/contact-mirror/rebuild` action to rescan all current Contacts, and compare counts with Salesforce before any later audience cutover. Rebuilding never removes current personal data on an incomplete scan. Reconnect only the same Salesforce org; a different org needs a reviewed migration rather than reusing these rows.

Before routing audiences through the mirror, validate row counts, sample identities, opt-out values, deletes, and a full rebuild against Salesforce. The next cutover should fetch Contact-only audience membership from local rows, keep Salesforce queries for related-object membership, then join those returned IDs to the mirror. Related-object changes require their own refresh strategy. Every campaign must still apply the suppression ledger and fresh-send consent checks; a daily Contact copy alone cannot be the final authority for an unsubscribe or a deliberate resubscribe. Only after parity checks should the redundant per-audience core Contact fetch be removed.
